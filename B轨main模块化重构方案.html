2 · 目标与非目标

目标
  • 可审查粒度：改哪块功能就只打开哪个文件；单文件上限从 843 行降到最大约 250 行。
  • 入口变薄：main.py 只表达「谁被装配、以什么顺序跑」，不表达实现。
  • 抗覆写：整份覆写的损失面从 46.8 KB 缩到约 14 KB（-70%）；实现代码落到从未被覆写的 vision/ 下。
  • 对外复用：显示层/识别线程/闭环调度都成为可被 target_api.py 或其它小问直接引用的组件。
非目标（本轮明确不做）
  • 不改运行时行为：日志字符串、串口帧、状态机时序、参数取值逐字不变。
  • 不追求性能提升：等价搬迁不会提升帧率。若要做热路径优化，须按项目铁律单独立项 + A/B 实测（见 §8）。
  • 不动算法与云台逻辑：rectangle_center.py / gimbal_*.py / stepper_link.py / config.py 一行不改。
  • 不动测试断言：两个入口测试必须零改动通过（兼容策略见 §6）。

6.2 为什么「相机 / 云台装配」必须留在 main.py

tools/test_main_self_test.py 用 patch.object(entry, "probe_imu", ...) 打桩到 main 模块的命名空间。 若把云台初始化搬进 vision/gimbal_boot.py，该 patch 就会失效（gimbal_boot 里的 probe_imu 不受影响，会调用真实实现）。 因此：云台装配保留在 main.py，抽成模块级私有函数 _init_gimbal(cfg)（仍属入口职责，约 45 行）， main() 只调用它。entry.time / entry.Config 的 patch 同样因为主循环仍在 main.py 而继续生效。

6.3 已识别的时序风险（必须实跑验证，不能只靠推理）

风险点：Clock 打桩只覆盖 main.time

test_main_self_test.py 把 entry.time 替换成每次 +0.02s 的假钟。搬迁后 VisionControl.process 内部的 time.perf_counter() 来自 vision/aim_control.py，不受假钟影响， 于是 fresh = now - captured_at <= RESULT_MAX_AGE_S 会恒为 False（真实时钟 vs 假钟起点 0）。

推理结论：这不影响三条断言的成立 —— 自检由 request_test 事件触发，与视觉新鲜度无关； 上电不来自检时本就不发运动帧。所以预期 三条用例全过， 但必须以 V3 步骤实跑为准；若失败，修法是给 VisionControl 注入 clock（而非改断言）。

8 · 后续可选优化（须单独立项 + A/B 实测，不在本轮）

本项目铁律：性能结论必须同进程交错 A/B。以下三条只是「模块化之后变得便宜」的候选，不得夹带进本轮重构：

  • FrameRate.values() 去 numpy 化：主循环每帧调用一次，内部有 np.diff / np.sort / np.append 三次分配。改纯 Python 可省分配，但相对 read/show 量级可忽略 —— 收益须实测，test_runtime_performance.test_real_fps 可兜底。
  • [perf] 增列 p95：read/draw/loop 目前只报均值，偶发长停顿看不见（low1 只覆盖帧率，不覆盖分相）。加 p95 是纯日志改动，无行为风险。
  • CameraSource 暴露 read_gray()：把「取帧 + 转灰度」合成一次调用，省掉主循环里 _to_gray(img, image) 对 image 模块的显式透传。
