一句话结论：B 轨的画面有三条独立时间轴——主循环负责「取帧 + 绘制 + 投递」，识别线程负责「识别 + 光斑偏差 + 云台闭环」， 显示线程负责「show() 上屏」。三者各自只取最新数据、以「最新槽位」解耦，任一侧变慢只表现为丢帧 / 标注滞后，不会互相拖垮。 显示层任何失败（无 maix、建屏失败、show 抛异常）都只停用预览，绝不影响识别与闭环。

1 · 显示管线数据流

主循环（蓝色）与识别线程（紫色）通过 submit() / snapshot() 两个「最新槽位」交互。 绘制阶段（橙色）发生在主线程，画完只把画布投递给显示线程 —— Display.show() 由显示线程执行，主循环不等它。

2 · 三条时间轴（务必分清）

轴 A主循环

决定屏幕刷新节奏。main() 内 while not app.need_exit()。

  • 取帧、转灰度、读触摸
  • 把当帧副本投给识别线程（不等待）
  • 取最新识别结果并按节拍绘制上屏
  • 周期打印 [perf] 日志

帧率口径：capture（取帧）/ disp（显示）

轴 B识别线程

决定识别吞吐。类 _LatestVision，daemon 线程。

  • 从最新帧槽取一帧 → 识别 + 光斑偏差 + 闭环
  • 结果写回最新结果槽
  • 无帧时走 idle()：收 ACK / 推进按钮自检
  • 独占 UART（收发不可并发）

帧率口径：detect_fps

轴 C显示线程

决定屏幕刷新。类 _Preview._show_loop，daemon 线程（SHOW_ASYNC=True）。

  • 取「待上屏画布」槽 → display.show() → 画布还池
  • 画布池固定 2 张；池空时主循环直接跳过该帧
  • 慢只慢预览本身，不回流拖累主循环 / 识别 / 闭环
  • 关停顺序：先停线程（等当前 show 做完）再 display.close()

帧率口径：disp；耗时口径：show avg/p95/max

为什么要拆三条轴：Display.show() 走屏幕驱动 / MaixVision 图传，单次可达数百毫秒；识别（Canny / 轮廓 / 单应）耗时不确定。 若同线程，则显示一慢就拖死识别、识别一慢屏幕就卡成幻灯片。
历史教训（v0.4.2）：只把「识别」拆出去是不够的 —— 只要 show() 还在主循环里同步调用， 主循环就被它按在地上，submit() 的节奏随之被拖死，识别线程再快也无帧可算（表现为三路帧率一起掉到同一低位）。 故 v0.4.3 把显示也拆出去。

3 · 主循环 8 步详解

1
取帧
img = cam.read()  （灰度 FMT_GRAYSCALE，640×480 @30fps）
读不到帧直接 continue，不污染后续统计。
2
转灰度
gray = _to_gray(img, image)
优先 image2cv(copy=False) 零拷贝借用相机缓冲；跨线程前必须 copy（下一步完成）。
3
触摸输入（按下沿）
if touch.poll(preview) == "selftest": controller.request_test.set()
只识别「上一帧未按、这一帧按下」，避免按住连触发；自检在线程内安全启动。
4
提交识别
worker.submit(gray, captured)
拷贝一份灰度图投入「最新帧槽」并唤醒识别线程。不等待；槽内已有旧帧则记一次 dropped。
5
取最新结果
snapshot, vision_fps, vision_low1 = worker.snapshot(now)
取回最近一次识别结果（可能滞后于本帧）。若识别线程报错则抛出终止。
6
过期降级
result, laser_state, age = _display_result(snapshot, now, RESULT_MAX_AGE_S)
age > RESULT_MAX_AGE_S（默认 0.2s）→ 用 {"valid":False,"stage":"stale"} 占位，不把旧框画成有效定位；视频原帧照常刷新。
7
绘制 + 上屏（节拍）
if preview.due(now): … preview.render(view, now, status=…)
按 SHOW_FPS 限频，且画布池有空位（否则本帧直接丢，不排队）。绘制顺序：draw_result 画框/角点/靶心 → draw_laser_overlay 画光斑面板与连线 → 左下角一行小字 → render letterbox 后投递给显示线程（不等 show）。
8
周期日志
每 LOG_INTERVAL（2s）打印 [perf] 行
三路帧率 + 分相耗时：read / draw / loop 属主循环，show avg/p95/max 属显示线程；另有 drop(show)（显示来不及）与 drop(vision)（识别来不及）。show p95 > 100ms 提示显示侧瓶颈，loop > 66ms 提示主循环侧瓶颈。

4 · 线程与节拍时序

下面示意「识别较快」与「图传较慢（show 卡顿）」两种情形下的实际行为：慢帧只让画面丢帧/滞后，识别与闭环不受影响。

5 · 屏幕元素布局

画布尺寸 = 物理屏幕尺寸（触摸坐标与按钮 1:1）。标注画面按等比例 letterbox 居中，两侧留黑边，不拉伸。

6 · 三个坐标系与 letterbox 换算

坐标系尺寸来源用途关键点
相机原图CAMERA_W × CAMERA_H（640×480） 识别输出坐标 (u,v)、四角、光斑位置 所有对外坐标都是这一套；detector.process 的输出
屏幕坐标display.width() × height() 触摸命中、按钮注册、画布尺寸 触摸返回的就是屏幕坐标 → 画布必须 = 屏幕尺寸才能 1:1
画布坐标render_width/height（SHOW_WIDTH=0 ⇒ 就等于屏幕尺寸） 实际送去 show() 的图 画布＝屏幕时 show() 零缩放，且与触摸坐标天然 1:1
letterbox 换算（_Preview.render）： scale = min(rw/vw, rh/vh) → 缩放到 (nw,nh) → 居中偏移 ox=(rw-nw)/2, oy=(rh-nh)/2 → 贴入画布。 相机 640×480 与屏幕 640×480 宽高比一致时，nw,nh == rw,rh：不缩放、不刷黑边，只剩一次整块拷贝。 两处「scale」不要混：
· draw_result 内部 scale = show_width / 原图宽（原图→缩小图）；
· draw_laser_overlay 的 scale = render_width / 原图宽（原图→画布），使光斑标记与框对齐。

7 · 关键配置项

配置默认作用
SHOWTrue是否建显示。False = 纯串口/头部模式，不流转画面。
SHOW_WIDTH0画布宽度；0 = 用屏幕原始宽度（画布＝屏幕 ⇒ show 零缩放，触摸 1:1）。>0 才缩小（省 MaixVision 带宽，但本机屏幕会被放大回全屏）。

8 · 隔离与降级边界

设计原则：显示是「最好有」，识别与闭环是「必须有」。显示层任何失败都只降级为「无预览」，绝不冒泡到识别/串口/电机。
失败点行为日志
SHOW=False不建 Display，直接 return[preview] SHOW=False -> 不建显示
建 Display 抛异常（无 maix / 设备占用）enabled=False，主循环不再绘制[preview] 显示初始化失败…
show() 抛异常（VO/fb0 卡死）就地停用显示[preview] show 失败，停用显示
无触摸屏 / 未启用按钮不可用，其余照常[touch] …（按钮禁用）
识别线程异常记录 worker.error，主循环下一轮抛出终止（不放任带病运行）[vision] worker failed: …

10 · 「只有 1.5 帧」的归因：一道串行阻塞链

2026-10-11 现场：屏幕画面约 1.5 fps。根因不是识别慢 —— 识别本身只占毫秒级； 真正的瓶颈是 Display.show()当时仍在主循环里同步调用，把「取帧 → 提交识别 → 绘制 → 上屏」 串成了一条链：show 慢多少，整条链就慢多少。

症状读数特征该动哪里
画面约 1.5 fpscapture / disp / detect_fps 同时偏低，而 read= 很小show 在主循环里阻塞 → SHOW_ASYNC=True
只有 disp 低capture≈30、loop 正常、show p95 偏大显示侧瓶颈：降 SHOW_FPS，正式追踪 SHOW=False
只有 detect_fps 低loop 正常、drop(vision) 增大识别吞吐瓶颈（与本页显示链路无关）
顺带修掉的一处浪费：相机 640×480 与 MaixCAM2 屏幕 640×480 宽高比一致，旧默认 SHOW_WIDTH=480 却把画面先缩到 480×360、再由 show() 放大回 640×480 —— 一次毫无收益的"缩了又放"。 现默认 SHOW_WIDTH=0（画布 = 屏幕）：零缩放，触摸坐标也不必再做比例换算。
为什么这不算过度设计：三个线程各自只保留最新一份数据 —— 没有队列、没有背压、没有跨线程等待， 任一侧变慢只表现为"丢帧"，永不阻塞另一侧。这是实时视觉系统应有的形态：宁可丢帧，不可积压。
