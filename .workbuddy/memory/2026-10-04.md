# 2026-10-04 工作日志

## 2025 电赛 E 题视觉——靶纸矩形框中心点识别（MaixCAM2 / MaixPy v4）

### 交付物（`vision/`）
- `find_center.py` —— 主程序。流程严格按需求：① 二值化锁定板框 → ② 描边(findContours 外轮廓)
  → ③ 找 x/y 极值四顶点 → ④ 排序成 TL/TR/BR/BL → ⑤ 对角线交点=靶心 → ⑥ A4 反算 px_per_cm
  → ⑦ One Euro 滤波 → ⑧ 绘制 + 可选 UART。主路径漏检时用原生 `img.find_rects` 兜底。
- `test_pc.py` —— PC 端合成透视靶纸图离线验证（无需硬件）。
- `debug_overlay.jpg` —— 可视化调试图。

### 关键技术结论（重要，勿重复踩坑）
1. **对角线交点=靶心是精确解**：透视成像是单应 H，"直线→直线、交点→交点"，
   矩形对角线交点必为矩形中心的投影。故本方案无需解 H 即可得到精确靶心（与"靶心红点不可见"的结论一致）。
2. **MaixPy v4 API 事实**：`find_rects` / `find_blobs` 确证存在；`find_contours` 无法从官方源码/文档确证
   → "描边"改用 OpenCV 桥接 `image.image2cv` + `cv2.findContours`（MaixCAM2 为 Ubuntu，可 pip 装 opencv-python），
   且能拿到完整轮廓点序列，正好满足"找极值顶点"的需求。
3. **极值法退化**：轴对齐（正视）时 min-x/min-y 会落到同一点，四顶点不足 4 个互异点
   → 已加去重 + 回退到 x+y / x−y 极值法。小角度/大角度旋转时极值法主路径生效且误差 ~0.02px。
4. **合成图真值约定**：真值必须用"像素中心"约定（黑框外沿为 (0,0)-(cw-1,ch-1)，中心 ((cw-1)/2,(ch-1)/2)）
   并用同一 canvas→image 单应投影，否则会出现 0.4px 假误差。
5. **Windows 中文路径**：`cv2.imwrite` 对含中文的路径静默失败，须用 `cv2.imencode(...)[1].tofile(path)`。
6. `findContours` 跨版本：用 `cv2.findContours(...)[-2]` 取 contours。

### 验证结果（合成图）
- 单帧中心误差 0.058px ≈ 0.003cm；多姿态 0.02~0.53px（≤0.06cm）。
- 100 帧加噪+失焦：检出率 100%，原始 σ≈0.01px，滤波后 σ≈0.003px（远优于 0.5px 目标）。
- 抗干扰（画面含 1.8cm 等效黑色赛道线）：通过。

### 待办
- 现场标定：EXPOSURE / GAIN / WB_GAIN（`Config` 内 TODO）；BLACK_THRESH 按实际黑白分布微调。
- 若轴上部署无 cv2，需 `pip install opencv-python numpy`。

## 二轮改造：改成 MaixPy 应用工程 + 解决"帧缓冲内存不足"（同日晚）

起因：用户反馈 ① 没有 `main.py`，不符合 MaixCAM 应用/烧录格式；② 运行时报"当前分辨率/格式下
算法需要的快速帧缓冲内存超过开发板可用内存"。

### 结构（已重构，旧 `vision/find_center.py` + `vision/test_pc.py` 已删除）
```
main.py（入口，名字固定）  app.yaml（Maix 应用描述）  config.py（标定+档位）  assets/icon.png
vision/{__init__,geometry,detector,overlay}.py     tools/{test_pc,smoke_main,make_icon}.py + maix_stub/
```
- MaixPy 应用规范：入口必须叫 `main.py`；`app.yaml` 字段 id/name/name[zh]/version/icon/author/desc/exclude；
  多文件项目用 MaixVision「运行项目」整包下发；打包 `maixtool release` → `app_store_cli install`。
- `vision/__init__.py` 故意不 import 子模块（避免把 cv2 强加给纯 geometry 使用者）。

### 内存问题的解法（关键）
1. **相机灰度直出** `image.Format.FMT_GRAYSCALE`（1 B/px）替掉 RGB888（3 B/px）；
2. `buff_num` 3 → 2；1280x720 摄像头缓冲 8.3MB → 1.8MB（约 4.6×）；
3. **两级解算**：缩小图(0.5)粗定位 + 靶纸外接框(±8%)内全分辨率精算 —— 省内存又不掉精度；
4. 删掉原来的 `img.find_rects` 全分辨率兜底（内部要生成梯度浮点图，内存大）；
5. 显示画布只分配一次并复用；`disp.show(image.cv2image(frame, bgr=False, copy=True))`；
6. 相机档位自动降级 + 启动打印 `maix.sys.memory_info()`；
7. 官方文档证实："高分辨率 + MaixVision 图像预览会因内存不足导致代码运行异常"；
   MaixCAM2 可改 `/boot/configs` 的 `maix_memory_cmm`。

### 新增结论（重要）
8. **两级解算把缩小图的系统偏置消掉了**：`WORK_SCALE` 取 1.0/0.75/0.5/0.375 单帧误差都是 0.0575px。
   （缩小图会造成 ±1 原始像素的**系统性**偏置，不是随机噪声，滤波救不回来 —— 必须靠 ROI 内全分辨率重解。）
9. 轴对齐姿态残余 0.25~0.53px 是"取极值像素"在半像素栅格上的约定，非算法缺陷。
10. **maix 桩模块 PC 预检**（`tools/maix_stub/` + `tools/smoke_main.py`）：3 秒查出 main.py 的
    API 误用/拼写，不必为一个拼写错误去板子上烧程序；还能验证档位降级。实测主循环逐帧 valid、
    显示路径走到、降级生效。
11. 注意 `from maix import sys` 会遮蔽标准库 `sys`（main.py 里用 stdlib sys 拼 sys.path）→ 用别名。

### 二轮验证结果（合成分辨率 1280x720，WORK_SCALE=0.5）
单帧 0.0575px≈0.0029cm；多姿态 0.018~0.53px（≤0.05cm）；100 帧检出率 100%，
σ_raw 0.008~0.010px、σ_filtered 0.002~0.003px；抗干扰通过。

## 三轮：修 ModuleNotFoundError: No module named 'config'（同日晚）

起因：上板运行报 `File "/tmp/maixpy_run/main.py", line 46 ... ModuleNotFoundError: No module named 'config'`。

### 根因（官方文档第七节明确）
MaixVision 左下角两个按钮语义不同：
- **「运行项目」**→ 整个工程文件夹打包下发到 `/tmp/maixpy_run/`，多文件 import 正常；
- **「运行当前文件」**→ **只发当前那一个文件**，工程里其它 .py 不会过去。

用户点的是后者，所以设备上只有 main.py。**这是使用方式问题，不是代码问题。**

### 处置（两种方式都能跑）
1. `main.py` 导入引导加固：`_find_project_root()` 依次探测 `__file__` / `__cwd__` / `__dir__` /
   `os.getcwd()` / `/tmp/maixpy_run` / `/root/apps`，找到含 `config.py` 的目录再入 `sys.path`。
2. 缺文件时 **`raise SystemExit(中文提示)`**（在 `import cv2/maix` 之前），直接告诉用户按 A/B 怎么办，
   不再抛裸 ModuleNotFoundError。判断用 `_missing_project_modules()`：`'config' in sys.modules` 时跳过
   （单文件版已把模块装进 sys.modules，不能误报）。
3. 新增 `tools/build_single.py` → 生成 `dist/main_single.py`（单文件自包含版）。
   实现：各模块源码用 `r'''...'''` 原样嵌入，运行时造虚拟 `vision` 包并 `sys.modules` 注册后 exec，
   于是 `from . import geometry as G` / `from config import Config` 不改一字即可工作；
   main.py 用 `exec(compile(src,'main.py','exec'), globals())` 保持 `__name__=="__main__"` 与 traceback 文件名。
   带 sha1 指纹清单，`--check` 可查出单文件版是否过期。
4. `tools/smoke_main.py` 升级为三项预检（模块化 / 单文件都测）：① 逐帧 valid 断言（39/39）② 档位降级
   ③ 模拟"只下发单文件"验证中文提示。桩 `display.py` 加 `shows` 计数器。
5. 顺手修 `detector._solve` 里 `WORK_SCALE=None` 时 `float(None)` 抛 TypeError → 兜底为 1.0。

### 验证
- 两入口主循环各 39/39 帧检出；三种姿态下模块化版与单文件版 **(u,v,scale) 逐像素完全一致**。
- `--check` 过期检测有效（改 detector.py 后正确报出）；重新生成后指纹一致。
- 全量回归 `tools/test_pc.py` 与二轮结果一致（0.0575px / 100% / σ 0.002~0.003px）。

### 新增结论（重要）
12. **MaixVision 运行方式决定下发内容**：多文件工程必须「运行项目」；要「运行当前文件」就得是单文件。
    板端代码位置：运行项目 → `/tmp/maixpy_run/`；装成应用 → `/root/apps/<app_id>/`。
13. 单文件打包的可靠做法：**源码嵌入 + 虚拟模块 exec**，比手工拼接（改写 relative import）更不容易出错，
    且能用 sha1 指纹防"改了源码忘了重新生成"。
14. `main.py` 里"缺依赖"的检查要放在 `import cv2/maix` **之前**，否则报错会先被第三方 import 掩盖。

## 四轮：修 cv2.error Bad number of channels (scn is 1)（同日晚）

起因：上板跑通启动后，主循环第一帧报
`cv2.error: ... Invalid number of channels in input image: 'scn' is 1`，
位置在 `to_gray` 的最后一行 `cv2.cvtColor(b, cv2.COLOR_BGR2GRAY)`（旧 main.py 第 162 行）。
先核对了 traceback 行号（245 / 279 / 162）与本地代码**完全一致** → 设备跑的不是旧代码，是真 bug。

### 根因（已复现确认）
**MaixCAM2 的 `image2cv(img, ensure_bgr=False, copy=False)` 对 GRAYSCALE 返回的是 3 维 `(H,W,1)`，
不是 2 维 `(H,W)`。** 旧代码用 `if a.ndim == 2` 判"灰度直出" → 判不出来；接着 3/4 通道分支也不匹配
→ 落到 `ensure_bgr=True` 兜底，而真机上 `ensure_bgr` 对灰度图是**空操作**（原样返回单通道）
→ 单通道数组喂给 `COLOR_BGR2GRAY` → 报 scn is 1。
本地用桩模块把形状设成 `(720,1280,1)` 后**逐字复现了同一条报错**（`VScn::contains(scn)`）。

### 为什么 PC 预检没拦住（重要的方法论教训）
桩模块的 `image2cv` 当初返回的是 **2 维**，于是"ndim==2 判灰度"这条正确分支在 PC 上永远走得到，
一上板就崩。**桩模块的返回值形状必须按真机实测来造**，否则预检只是自我安慰。

### 处置
1. `main.py` 新增 `_as_gray(a, bgr=False)`：**按实际 shape 判断**，不再按"请求了什么格式"猜。
   `np.squeeze` 先去掉长度为 1 的哑轴（覆盖 `(H,W,1)` / `(1,H,W)` / `(H,1,W)`），
   再按 2 维 / 3 通道 / 4 通道分别处理；都不行返回 None，交给 `ensure_bgr=True` 兜底；
   兜底也失败则抛带 shape/format 的明确 RuntimeError。`np.squeeze` 返回视图 → 零拷贝保持。
2. `to_gray(img, debug=False)`：首帧打印 `[gray] format=.. shape=.. dtype=.. ndim=..`，
   由 `Config.DEBUG_SHAPE`（默认 True）控制。换板子/固件时一眼确认走对分支。
3. 桩模块 `tools/maix_stub/maix/image.py` 重写：新增 `GRAY_AS_3D`（默认 True，模拟真机），
   `image2cv` 对灰度按该开关返回 2 维或 3 维；`ensure_bgr=True` 对灰度原样返回（与真机一致）、
   对 2 通道按 RGB565→BGR888 模拟转换。`Image.format()` 兼容带哑轴的数组。
4. `smoke_main.py` 新增**预检 4/4：灰度形状矩阵**——7 种输入形状逐个断言，
   再把桩切成 `GRAY_AS_3D=False` 整跑一遍主循环（两种固件约定都覆盖）。
5. 桩 `app.py` 补 `reset()`，`smoke_main.run()` 每次跑前清零。**桩的退出计数是模块级全局的**，
   同一进程里跑第二次 main() 会立刻退出（表现为"检出 0/0 帧"）——踩过一次。

### 验证
- 首帧日志 `[gray] format=1 shape=(720, 1280, 1) dtype=uint8 ndim=3`，检出 39/39 帧。
- 形状矩阵 7/7 OK；GRAY_AS_3D True/False 两种约定各 39/39。
- 反向验证：同一输入喂给旧逻辑 → 复现 `VScn::contains(scn)`；新逻辑 → `(720,1280) uint8`。
- 模块化 / 单文件两入口 + `test_pc.py` 全量回归通过（0.0575px、100%、σ 0.002~0.003px）。

### 新增结论（重要）
15. **`image2cv` 返回形状各固件不统一**：MaixCAM2 灰度给 `(H,W,1)`。永远按 shape 判断，
    永远先 `np.squeeze` 去掉哑轴，不要靠 `ndim==2` 认灰度。
16. 真机上 `image2cv(ensure_bgr=True)` 对**灰度图是空操作**（灰度没有 BGR 形式），
    所以"用 ensure_bgr 兜底"这条路对灰度无效——兜底必须能处理单通道。
17. **PC 预检的有效性取决于桩的保真度**：桩返回的形状/类型与真机不一致，预检就会漏掉真机必崩的 bug。
    凡是"从设备 API 拿数据"的地方，桩都要按实测形状造假。

## 五轮：评估"另一条技术路线"（Canny+多边形逼近 / 内外框 / 8x8单应 / 圆映射）

用户提出新路线：① Canny+多边形逼近定四角 → ② 沿边采样内外灰度差区分内外框 →
③ 建 8x8 线性方程组高斯消元解映射参数 → ④ 正视面 1px=1mm 建坐标系 →
⑤ 72 等分采样标准圆逐点逆变换回原图像素。
产出 `tools/exp_alt_pipeline.py`（A 检测器 / A2 内外框 / B 亚像素 / C 单应数值 / D 圆映射 / E 尺度对照）。

### 实测结论（合成图，1280x720）
18. **检测算子对"中心"几乎无影响**：阈值+轮廓(极值顶点) 中心误差 0.7347px；Canny+approxPolyDP 0.7496px
    —— 同一量级。耗时也几乎相同（1.80ms vs 1.77ms/帧）。真正把中心压到 0.06px 的是**亚像素边缘精修**。
    => 不要为"换 Canny"付出代价，收益为零；Canny 唯一实质代价是**瞬时内存峰值**
    （Sobel 需 2 张 CV_16S 梯度图 + 幅值图，1280x720 多 3~4MB 临时缓冲，稳态 WS 探针看不见）。
19. **approxPolyDP 的 eps 宽容区间**：[0.005, 0.08]×周长 都给 4 个顶点（0.001→5 点，0.15→3 点）。
20. **拿到内框不用采样灰度差**：`cv2.threshold(INV)` + `findContours(RETR_CCOMP)` 一次调用同时给出
    外轮廓(父=-1)与内孔轮廓(父≠-1)。外/内框中心差 0.2664px（用对角线交点；切勿用图像质心比，
    透视不保质心，会得到 7.14px 的假差异）。灰度梯度符号确实能区分外沿/内沿，原理成立但没必要。
21. **亚像素方法排序（中心误差）**：极值顶点 0.735 → 二值轮廓 fitLine 0.0575 → 灰度梯度剖面 0.1030
    → **fitLine 后接梯度剖面 0.0258（最优）**。梯度剖面能更贴近真实边缘（角点 0.73→0.37px），
    但单独用不如现状；作为**第二级**叠在 fitLine 之后才最优。
22. **8x8 高斯消元本身没问题**：无噪声下自写高斯消元中心误差 1.1e-13px，与 cv2.getPerspectiveTransform
    一致。但原始像素坐标下 8x8 条件数 **4.55e5**，归一化(Hartley)后 **3.08**。float64 下无所谓
    （丢约 6 位仍剩 10 位），**float32 下会掉到约 4.5% 相对误差 → 板上若用 fp32 必须先归一化**。
23. **用内框当第 2 组对应点确有价值**：8 点最小二乘 vs 4 点，σ=1px 时中心误差 0.9872 → 0.6794px
    （约 1/√2）。而且 8 点重投影残差可当"模型失配体检指标"。
24. **镜头畸变是单应模型之外的误差，加对应点救不了**：k1=-0.15 时 4 点 1.5785px、8 点 1.4032px
    —— 只降 11%。畸变必须靠 `undistort`/标定单独解决，不能指望多点 LS。
25. **★ 标量 px_per_cm 根本不成立（这是本路线最大的价值点）**：
    同一靶心处 **横向 22.76 px/cm、纵向 16.71 px/cm（比 1.36）**，`estimate_scale()` 返回的单一标量
    19.98 px/cm 是两者平均 → 任一方向必然错 36%。
    量胶带宽（真值 18.0mm）：**标量法 21.07mm（+3.07mm，17% 误差） vs 单应法 18.09mm（+0.09mm，0.5%）**。
    => 凡是要"像素↔毫米"的度量（打环半径、圆轨迹、偏差量），**必须用单应**，标量换算不可用。
26. **第 ④ 步"1px=1mm"只是坐标记账**：本画面靶心处横向已有 2.28 图像像素/毫米，标到 1px=1mm
    等于降采样 2.28 倍；合理等效分辨率是 ~478px 宽而非 210px。但**只做 72 个点的变换、不做整幅 warp 时，
    工作面的缩放无关紧要**——精度由原始像素决定，不由 mm 网格决定。切勿每帧真的 warpPerspective 一张
    297x210 图（凭空多一次重采样+分配，板上内存要紧）。
27. **圆映射自洽性**：mm→px→mm 往返误差 8.6e-14mm；半径 40mm 的圆映射后是轴比 1.3677 的椭圆，
    与 22.76/16.71=1.36 完全吻合 → 方向约定（哪边取逆）验证正确。

### 结论：路线可行，但值得要的只有一半
- **要**：③ 单应（解决 25、26 两个真问题）、⑤ 圆映射（数学自洽）、② 的"梯度剖面"思想（作第二级精修）。
- **不要**：① Canny 取代阈值（收益 0，多 3~4MB 瞬时内存）、② 用灰度差找内框（层级法一次就有）、
  自写高斯消元（`np.linalg.solve`/cv2 更稳，且要注意归一化）。

## 六轮：透视/视角鲁棒性验证 —— 发现并修复"绕光轴旋转约 45° 漏检"缺陷

起因：用户问"现在的代码能否解决透视变换问题、保证视角不一致时矩形框变形"。
产出 `tools/exp_perspective.py`（真实针孔相机模型 + 俯仰扫描 + 各向异性 + 单应校正验证
+ 顶点路径对比 + 组合姿态）与 `tools/exp_perspective.jpg`（误差/各向异性-角度曲线）。

### 结论 A：中心定位本就不受透视影响
以真实针孔模型扫俯仰 θ=0~65°：误差 0.006~0.47px，**无随角度增长的趋势**（波动是单帧噪声）。
42 个（俯仰 6 档 × 光轴旋转 7 档）姿态组合**全部检出**，误差 0.003~0.448px，无死区。
=> "矩形框在图像里变成梯形"这件事**不需要消除**：对角线交点是射影不变量，
   矩形中心(靶心)的投影恒等于两对角线交点 —— 这是精确解，不是近似。
θ≥70° 会拒检（`is_valid_quad` 的 ASPECT 上限拦下，属**安全失败**：宁可 NOT FOUND 也不给错值）。

### ★ 结论 B：发现并修复真实缺陷 —— 靶纸绕光轴旋转约 45° 时漏检
- 现象：roll = 40/44/45/46/50° **全部 NOT FOUND**。
- 根因（两层，都在 "x+y / x−y 极值" 这个思路上）：
  1) **取点**：s=x+y 与 d=x−y 的梯度方向只差 90°，靶纸边方向接近它们时两个极值落到**同一个角**，
     4 个候选点里"缺一个角、另一个角被取重"。
  2) **排序**：`order_corners` 也用 x+y/x−y，roll≈45° 时 s、d 出现**并列极值**
     （A4 竖放转 45°：TL 与 BL 的 x+y 相等），同一个角被排进两个位置 → 四边形退化 → 拒检。
- 修法：
  1) `order_corners` 改**质心极角排序**（凸四边形按极角排序必得正确环序），去掉 45° 奇点。
     起点仍取 x+y 最小者（仅为标签可读）—— **起点循环移位不改变两条对角线的集合**，故不影响靶心。
  2) `order_corners_by_sumdiff` 改**多方向极值候选**（x/y 极值 + x±y 极值共 8 个）去重；
     多于 4 个时用 `_best_quad` 取**凸包面积最大**的 4 个（穷举 C(n,4)，n≤8）。
  3) `extract_ordered_corners` 的 extreme 分支补 `_too_thin()`：x/y 极值会出现
     "同一角的两侧边缘点相距十几像素、躲过去重"的情形，使 4 点退化成三角形（实测对边比 **58**）。
     **注意：极角排序后这类退化四边形反而能通过 `is_convex`**，所以必须显式查"对边比"。
  4) `detector._polygon_quad`（凸包 + approxPolyDP）作最终兜底（极值法全失效时）。
- 差点引入的回归：改完 `order_corners` 后精度 0.0575→0.0610px（差 0.0035px，可忽略），
  但 method 标签从 sumdiff 变成 `hull0.010`（兜底被频繁启用）——正是因为退化四边形
  现在能通过 `is_convex` 而"抢下"主路径。补 `_too_thin` 后主路径恢复。

### 结论 C：标量 px_per_cm 的方向性误差随倾角爆炸
各向异性 sx/sy：0°=1.00（标量误差 0.2%）、30°=1.15（4.5%）、45°=1.41（10.0%）、65°=2.37（21.4%）。
与五轮结论 25 一致：**涉及"像素↔毫米"必须用单应**，标量只够粗判量级。

### 结论 D：单应确实能"校正"透视变形
用**检测到的外框 4 角**建 H(mm→px)，把**内框 4 角**（不在建单应的点集里）逆映射回 mm：
θ=0~50° 全部回到 (18,18)-(192,279)mm；宽 172.6~173.4（真值 174）、高 260.3~260.9（真值 261），
最大偏差 0.91~2.49mm。=> 要在靶纸上做毫米级操作（画环、报偏差）时，单应可用且够准。

### 验证
`test_pc.py` 单帧 0.0610px、100% 检出、σ_raw 0.008~0.012px、抗干扰 PASS、WORK_SCALE 无关；
模块化/单文件两入口预检 4 项全 PASS；单文件版已重建（指纹一致）。

### 新增结论（重要）
28. **对角线交点=射影不变量，"透视变形"对靶心定位根本不是问题**；需要"消除变形"的只有毫米度量。
29. **45° 是 x±y 极值法的奇点**（取点与排序都会坏）——凡用 x±y 做角点/排序的地方都要警惕。
30. 凸四边形排序的正确做法是**质心极角排序**；起点选谁无所谓（对角线集合对循环移位不变）。
31. 退化检查不能只看 `is_convex`：极角排序会把"缺角/重角"的四边形也排成凸的，必须另查对边比。
32. 合成验证要用**真实针孔模型**扫参（而非手挑几个四边形），才能定位到"某个角度区间失效"这种规律性缺陷。

## 第六轮（2026-10-04 r5）：真机"锁框效果很差" —— ② 描边策略重构

### 问题
用户反馈真机上"框选不出/锁不住"。合成图测试一直全绿，说明**测试集太理想**，
必须先把真机的恶劣条件造成测试集复现出来，再改（不能凭猜改代码）。

### 复现（tools/test_hardscene.py，按反射率模型造 12 个硬场景）
`gray = clip(照度场 × 反射率 + 环境杂散光 + 噪声)`；胶带 0.07 / 纸面 0.85 / 亮墙 0.62 / 暗墙 0.055。
**旧策略（取面积最大的黑轮廓）8/12 失败**：过曝、欠曝、环境光大、暗背景、暗背景+高照度、
暗角、反光(偏4px)、干扰物更大(偏107px)。

### 根因（最重要的一条）
1. "取最大黑轮廓"在真机上极易锁错：深色背景/桌面/干扰物比胶带框更大；框贴边时轮廓被画面切断。
2. **胶带一旦与任何深色区域相邻（暗背景、干扰物、阴影），两者在二值图里连成一片，
   胶带的外沿就不再是闭合轮廓** —— 此时无论怎么调阈值都取不到环。这是调参救不了的。
3. 但这时**纸面（亮面）的轮廓始终完好**：纸面被深色胶带围着，是一块干净的亮矩形。

### 解法：两族互补候选（核心思想）
- `ring`（深色环）：黑胶带**外沿**。中心最准（贴着纸边），但会被深色背景吃掉。
- `paper`（亮面矩形）：纸面 = 胶带**内沿**。抗上述所有破坏，但胶带贴不均匀时中心会偏一点。
- 两者同心（内沿 = 外沿向内收 1.8cm），中心都能用。**优先 ring**（`RING_BONUS=0.08`），
  分数接近时取外沿；ring 拿不到才用 paper。运行时 `[fps]` 行打印 `候选=ring/paper` 可辨。
- 尺度换算随之分两种：ring 用 A4 外沿 21×29.7，paper 用内沿 17.4×26.1（`estimate_scale(inner=)`）。

### 判据（全部旋转/透视不变，不依赖角点排序）
`fill`（轮廓/最小外接矩形）、`aspect`（最小外接矩形长宽比）、`rim`（内孔/外框，胶带环≈0.73）、
`ring`（环厚/外框，1.8cm/21cm≈0.07）、`hole_fill`、`contrast`（亮面灰度 − 深色带灰度）、
`border`（贴边即否决）、`parent_area/area`（亮面族要求外围深色区更大）。

### 阈值自动标定
- 候选阈值 `fixed` + `otsu` 都试，用同一套结构分择优；胜出后**锁定**，稳态零额外开销；
- 连续 `THRESH_RELOCK_MISS=3` 帧失败才解锁，用 `THRESH_SWEEP`(30…205 共 10 档) 重扫。
- 两个"阈值合理性"硬约束：掩膜前景占比须在 `[MASK_FG_MIN, MASK_FG_MAX]=[0.002,0.93]`
  （太低=什么都切不出；太高=把背景都当深色）。

### 踩到的坑（务必记住）
36. **`_soft()` 的区间语义用错了**：对比度是"越大越好"，我却写成"区间内才好"，
    结果**对比度 233 被算成 0 分**，正确的纸面候选少 0.35 分、被错误的伪环挤掉。
    → 新增 `_rise(x, lo, hi)`（越大越好）专用于对比度这类量；`_soft` 只用于"区间内才好"的量。
37. **"打分全失败就退回最大轮廓"的兜底必须关**（`SCORE_FALLBACK_LARGEST=False`）：
    开着它，"有矩形外形但不是环"的东西（实心深色块、黑板、纯墙渐变区）会被救回来变成
    "合法四边形"，**误锁到完全错误的位置**。误检比漏检更糟（云台会照着错位置打）。
38. **硬否决 vs 软分项**：`PAPER_MIN_CONTRAST` 一开始只做软分项，结果"亮块贴在亮墙上、
    把阈值拉到比墙还高"这种假框（对比度只有 69）照样通过。→ 必须做**硬性否决**。
39. **测试集本身也会错**：原来的"近端大目标"预设把**竖版 A4 映成了横版**（宽>高），
    这不是真实相机能拍出的像 → 它导致的"未检出"是测试集的错，不是算法的错。
    造场景要保证物理可解释（用针孔/单应模型，别随便填四个点）。
40. **反向验证（误检）和正向验证一样重要**：只测"能不能锁住"会把算法调成"什么都敢锁"。
    必须先加"画面里没有靶纸"的负样本集（纯墙 / 深色实心块 / 亮块贴亮墙 / 一条深色横线 / 大黑板）。
41. `np.hstack` 拼图后算宽度要用 `t.shape[1]`，**`len(t)` 取的是高度**（拼图被裁成 225 宽）。
