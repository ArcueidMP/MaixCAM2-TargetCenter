## 22:40–23:0x B 轨 v0.4.3：显示移出主循环 —— 修「只有 1.5 帧」

**用户报告**：画面只有 1.5 帧；要求检查代码冗余。**关键澄清**：看到 1.5 帧时**电脑端 MaixVision 未连着**

- **定案根因（写进 README 与 HTML）**：不是识别慢。`Display.show()` 当时仍在**主循环里同步调用**，
  于是 `cam.read → submit → 绘制 → show` 串成一条链：**show 慢多少，整条链就慢多少**。
  `submit()` 节奏被拖死 ⇒ 识别线程无新帧可算 ⇒ `capture`/`disp`/`detect_fps` **三路一起**掉到同一低位。
  ⚠ 顺带证伪一个直觉：`preview.due()` 的"固定时间轴限频"在这条链上**被架空**（show 阻塞后 `now>=_t_show` 恒真），
  **把 SHOW_FPS 降到 5 也无效** —— 别再靠调这个配置治该症状。
- **MaixCAM2 屏幕 = 640×480**（官方硬件参数确认，仅此一种屏），与相机 640×480 **宽高比一致**。
  旧默认 `SHOW_WIDTH=480` 会把画面先缩到 480×360、再由 `show()` 放大回 640×480 —— **纯来回折腾**。

## 板端复测（v0.4.3）→ 定位真凶 → v0.4.4 探针

- **板端实测**（v0.4.3，用户贴回）：`capture=2.5 disp=1.9 detect_fps=0.0 | read=106.9 draw=13.9 loop=321.2ms |

- **根因（源码级确证，不是算力）**：`show` 的 avg/p95/max 挤在 505~509ms = **固定超时**。
  MaixCDK `components/vision/src/maix_image_trans.cpp` 的 `send_image()`：
  `if(!handle->init){ while(!init){ if(ticks-t>500) return ERR_NOT_READY; } }` ——
  **处于 MaixVision 模式但图传 websocket 未连上时，每次 show() 忙等 500ms 并空转 CPU**。

  相机 read 被抢到 107~175ms、loop 321ms、识别线程饿死（detect_fps=0）。**本地屏官方只要 1~5ms**。
